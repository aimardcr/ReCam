# ReCam latency baseline — 2026-11-08

Measured on the connected 2409FPCC4G, Android 16 / API 36, ARM64. Source was
FFmpeg `testsrc2`, libx264 ultrafast/zerolatency, no B-frames, 30 fps, over USB ADB.
Both 25-second runs served the stock camera app's **1440×1080** lane. Source sizes
were 1280×720 and 1920×1080; both therefore exercised the scalar scaling path.

The first three seconds and nominal final second were excluded. These are
percentiles of a **growing backlog**, not a steady-state latency guarantee.

| Device stage (ms) | 720p p50 | 720p p95 | 1080p p50 | 1080p p95 |
|---|---:|---:|---:|---:|
| Userspace receive → codec submission | 2441.91 | 3919.88 | 2177.54 | 3632.49 |
| Codec submission → output dequeue | 796.67 | 948.93 | 771.27 | 959.61 |
| Output dequeue → CPU copy complete | 0.85 | 2.53 | 1.27 | 3.32 |
| Scaling into ring | 15.88 | 21.04 | 16.00 | 18.98 |
| Ring publication → camera copy start | 20.45 | 88.62 | 19.98 | 84.55 |
| Copy into camera planes | 1.80 | 11.36 | 1.76 | 11.13 |
| Userspace receive → camera copy complete | 3270.76 | 4749.82 | 3000.22 | 4446.73 |

Device read-to-camera-copy p99 was **4888.60 ms** at 720p and **4568.98 ms** at
1080p. The runs captured 833 / 830 matched consumption events, covering 464 / 475
unique lane publications. Repeated consumption of the same frame is included:
that is the age of the pixels actually supplied on each callback. Publication
metrics use 525 / 533 samples; stage percentiles must not be added together.

## Backlog and interpretation

The stream produced 30 fps, but profiled frame publication sustained only about
**25.01 / 25.43 fps**. Median receive-to-publication age grew from **1.65 to 4.66 s**
in the 720p run and **1.58 to 4.37 s** in the 1080p run, comparing the first and last
three-second buckets of the retained measurement window.

A separate 720p run with profiling disabled, direct FFmpeg→ADB TCP, and **no
camera preview or scaling** still showed about **25.30 decoded fps**. Its queued
compressed bytes grew from 1,075,096 to 3,306,603 across the final sampled
15.06 seconds. This corroborates backlog without the per-frame instrumentation.
It is not a matched workload comparison and does not quantify profiling overhead.

The measured dominant delay is inside the device, before codec submission and
between submission and output dequeue. The latter includes MediaCodec buffering
and the feeder's polling/scheduling; it does not isolate hardware decoding time.
The current loop submits input before draining output and consumes one decoded
frame per tick. Those are candidates for the next controlled experiment, not a
confirmed single root cause. No transport or scheduling optimization was applied.

## Host endpoint and uncertainty

Encoded-byte proxy ingress → camera-copy completion estimates:

| Source | p50 | p95 | Clock uncertainty |
|---|---:|---:|---:|
| 720p30 | 3215.50 ms | 4708.68 ms | ±122.39 ms |
| 1080p30 | 2951.59 ms | 4385.48 ms | ±127.07 ms |

Host/device clock offsets were bounded by status-request round trips before and
after each run without assuming symmetric paths. The report uses the envelope of
those bounds and assumes the offset stayed within it during the run. That
uncertainty is too large to isolate USB/ADB transport latency; host-to-receive
midpoint estimates can even be negative within the uncertainty interval.

Capture and encoding occur before the host endpoint. Buffer unlock, delivery to
the app, and display occur after the device endpoint. This is **not glass-to-glass
latency**. A local proxy and per-frame logcat instrumentation add overhead.
Receive timestamps mark userspace reads, not arrival in the kernel socket buffer.
Only one device and one camera output size were tested, with one run per source
size. The slightly lower 1080p numbers do not establish a resolution advantage.

## Reproduction and evidence

See [README profiling instructions](../README.md#latency-profiling). The instrumented
code is based on lifecycle commit `016bebf`. Run the same command with a fresh
output directory, leave the unlocked camera preview open, and repeat several times
before comparing future optimizations.

- [Full measured statistics and clock samples](latency-2026-11-08.json)
- Raw local evidence: `.scratch/latency/720p-active/` and
  `.scratch/latency/1080p-active/` contain `device.log`, `host_chunks.json`,
  `command.json`, `ffmpeg.log`, and `report.json`.
- Profiling-disabled control: `.scratch/latency/control-720p/`.
- The first `.scratch/latency/720p/` attempt had no camera stream while the phone
  was locked and is excluded.

ARM64 and x86_64 builds passed. The receive-timeline and analysis regression tests
passed, including byte-boundary matching, clock-bound arithmetic, and exclusion of
post-stream stale frames. The existing 63 device self-tests also passed. The feeder
and hook were stopped after validation.
