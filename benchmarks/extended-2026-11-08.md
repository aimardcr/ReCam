# Extended validation — 2026-11-08

This pass adds a timed soak, a second Android-version check, and source-frame
identification in compositor screenshots. Optical capture-to-display latency
remains unmeasured because a second camera was unavailable.

## Scope of the screenshot measurement

`tools/profile_compositor.py` generates 30 fps synthetic QR frames, records each
frame's host-monotonic generation time, encodes with the normal desktop FLV
settings, and matches identifiers in `adb exec-out screencap -p` output.

For a matched frame generated at G, screenshot request start S, and first PNG
signature arrival H, its age when sampled is bounded by `max(0, S-G)` and `H-G`.
All three timestamps
use the same host clock. This includes QR generation, encoding, forward transport,
decode/scale, camera delivery, and app composition. It excludes physical source
capture and display-panel scanout/response. Frame age at a sampled snapshot is
not the latency to its first presentation. Screenshot overhead perturbs the
device and widens the interval; these are bounds, not midpoint latency estimates.
The QR scene is simpler than ordinary camera content. Android captures and locks
its image before emitting PNG bytes; receiving the signature therefore bounds
capture without waiting for the rest of compression and transfer.
[AOSP screencap source](https://android.googlesource.com/platform/frameworks/base/+/master/cmds/screencap/screencap.cpp)

The initial tool used full screenshot completion as the upper bound. On the phone,
all 30 samples decoded at each source size, but median round trips were 742/662 ms
and median upper bounds 541/512 ms (720p/1080p). These were too loose to characterize
the pipeline. The final tool records header arrival separately from response end.

## Android 12 / API 31 ARM64 emulator

A fresh disposable AVD used the installed Google APIs ARM64 image with fingerprint
`google/sdk_gphone64_arm64/emulator64_arm64:12/SE1A.220630.001.A1/9056438:userdebug/dev-keys`.
SELinux stayed **Enforcing**; root adbd supplied the injector privileges. The
existing user AVDs were untouched. This is another Android version, not another
vendor SoC or x86_64 runtime. The disposable AVD was stopped and deleted afterward.

The full `recam test` attempt crashed the host emulator graphics process with
`Unhandled GL format 0` / `Failed to convert gl-format:0 framework-format:0`.
That test did not pass. Component testing proceeded after restarting the AVD.

Eleven standalone programs passed: FLV bounds/fixture parsing, scaler differential
checks, preflight parsing, CLI exit, receive timeline, mocked codec scheduling,
concurrent hook shutdown, payload lifecycle, remote errno, ring cleanup, and real
MediaCodec stream decoding. The real decoder accepted FLV and Annex-B, returned
320×240 nonempty pixels, and completed without codec errors or EOS timeouts.
Four initial test binaries needed rebuilding with a static C++ runtime because
the clean image had no `libc++_shared.so`; the documented commands now do this.

The emulator exposed a separate file-loading fallback bug: repeated injection
overwrote the same staging pathname while an earlier payload remained mapped.
One reinjection returned to the old base and crashed during initialization with
PC `0xbaf0`; cameraserver restarted. The phone's memfd route did not exercise this.

The fix stages each load in a fresh inode/path and unlinks the pathname after the
remote loader is done, including error paths. It does not overwrite or unload
earlier mappings. A native regression verifies distinct inodes and intact older
mapped bytes. With build **518f1934e2ff7f44**, ten idle reinjection/stop cycles
passed, each using a different payload base, with PID **4853** unchanged. Eight
additional mixed-resolution live cycles passed in **38.67 seconds**, with **367**
distinct live publications consumed, no fatal logs, and the same PID.

An eight-screenshot compositor smoke test decoded eight changing frame IDs.
Median source-frame age was bounded by **29.80–98.35 ms**; the corresponding p95
bounds were **49.52–119.97 ms**. Median screenshot round trip was **64.61 ms**.
This smoke test used the earlier full-response bound. These emulator numbers
validate frame matching and are not comparable to phone latency.
The preview's served lane was 320×240; an additional 1856×1392 request exceeded
the documented frame-ring size cap and received pattern fallback.

## Phone soak and compositor measurements

The physical POCO Android 16 device passed **212 cycles in 1800.82 seconds**
(30 minutes), using build **8657d68133075843**. It predates only the file-route staging fix;
the phone uses memfd loading. The host emulator ran during the first part of the
soak, so host load was not held constant. This is a stability test, not a matched
latency comparison. The run consumed **10,053 distinct live publications**, had
**zero fatal log events**, and retained cameraserver PID **22358** throughout.
All 212 cycles logged frame-ring reclamation. Stopped-state RSS grew from
**94,852 to 111,696 KiB** (16.45 MiB net; final value also the peak). Final state
had no feeder, active hook, or ring. Each of the four modes ran 53 times.

| Mode | Median of per-cycle p50 frame ages | Largest observed frame age |
|---|---:|---:|
| Disconnect | 65.69 ms | 650.91 ms |
| Stop while live | 63.89 ms | 467.14 ms |
| Pause/resume | 123.58 ms | 2045.94 ms |
| Reconnect | 62.38 ms | 567.61 ms |

The runner records stopped-state RSS, distinct live frames consumed, crashes,
camera-service PID, and per-cycle receive-to-copy frame age. Frame-age distributions
include startup, deliberate stalls, EOF, and repeated use of the last frame;
they must not be compared directly with warmup-trimmed healthy-stream benchmarks.
Pattern/file fallback is expected after the two-second live-input stall threshold.
Payload images/trampolines remain intentionally mapped, so some growth with the
number of injections is expected even after frame rings are reclaimed.

The first header-bound attempt matched 28/30 samples at 720p and 29/30 at 1080p,
so neither was marked as passing. The 720p run recorded one ring overrun and one
screenshot of color-bar fallback. Two other misses were valid QR images decoded
successfully after downscaling offline. Their generation timestamps had not been
persisted, so those missing timing samples were not reconstructed or interpolated.
The final tool retries detection at half and quarter resolution and saves every
source-frame generation timestamp. The observed fallback under screenshot load remains a
limitation; passing the lifecycle soak does not establish zero visible fallback.

The final repeat collected 30 screenshots per source size with approximately
30 generated fps and no reported ring drops. All 30 720p IDs decoded during
collection. One 1080p ID required quarter-resolution offline detection using its
saved original screenshot and exact source timestamp. `report.json` retains the
original failed collection status; `analysis.json` records that recovery and all
30 matched samples. The tool now includes that detection scale.

| Source | Matched frames | Median frame-age bounds | p95 frame-age bounds | Median full screenshot round trip |
|---|---:|---:|---:|---:|
| 720p | 30/30 | 0–187.90 ms | 0–249.09 ms | 689.15 ms |
| 1080p | 30/30, one recovered offline | 0–210.70 ms | 0–251.00 ms | 789.42 ms |

Every lower bound was zero because the matched source frame was generated after
the host screenshot request began. Header arrival still includes capture-request
scheduling and some compression/transport overhead. These intervals cannot locate
latency precisely inside that range or establish a 720p/1080p performance ranking.
They also do not replace an optical measurement. Final phone build is
**518f1934e2ff7f44**; cameraserver PID remained 22358. The tapper was stopped before
phone compositor sampling; one preview tap preceded each run, followed by warmup.
No feeder, active hook, or frame ring remained after testing.

## Reproduction and evidence

```sh
python3 tools/stress_lifecycle.py --serial DEVICE_SERIAL --minutes 30 \
  --alternate-sizes --output .scratch/extended/new-soak
python3 tools/profile_compositor.py --serial DEVICE_SERIAL --samples 30 \
  --size 1280x720 --output .scratch/extended/new-compositor
```

The compositor tool needs Pillow, qrcode, and opencv-python-headless. Both require
an unlocked live preview and an initially stopped ReCam session. Add `--adb-root`
for root-adbd userdebug emulators. The soak uses a dedicated dynamically allocated
host port, so multiple devices can be tested concurrently. The 30-minute phone run
began before that port-allocation change and used the original fixed forward.

Local raw evidence is under `.scratch/extended/`: `soak-30min/`, the guarded
20-second preview tapper log, and `emulator/` (native results, pre-fix failure logs,
file-route cycles, live cycles, and screenshot samples). The full-gralloc crash,
initial runtime-linking failures, and an obscuring Camera error dialog are retained
as failed attempts rather than included in successful measurements.

[Machine-readable evidence](extended-2026-11-08.json) includes all six phone
compositor attempts, the final offline analysis, the full timed-soak rows, and
emulator results. Original screenshots and `source_frames.json` are retained
locally in `compositor-final-720p/` and `compositor-final-1080p/`. Re-analysis uses
`decode_frame`, `age_bounds`, and `distribution` from `tools/profile_compositor.py`;
only decoded IDs with a saved generation timestamp receive timing bounds.
